# 비공개 접수와 로컬 작업기 연결 v1

기준: Draft PR #12 (`e11af0e`). Phase 1의 로컬 실행 상태·격리 경계 개발 단위다. 실제 AI 인증이나 게임 개발 작업을 시작하는 운영 기능은 아직 열지 않는다.

## 구현한 경로

1. 기존 읽기 전용 수신기로 받은 `received` 접수증을 다시 읽는다. 접수증에 고정된 manifest SHA-256, 각 입력의 크기·SHA-256, 라우팅을 재확인한다.
2. Git 밖의 별도 0700 상태 디렉터리에 입력 스냅샷을 복사한다. 파일은 0600이며 기존 작업 디렉터리를 덮어쓰지 않는다. 수신 데이터가 뒤에 바뀌어도 준비된 입력은 별도로 보존한다.
3. `local-v2` 암호화 문맥은 작업 ID, 무작위 UUID 실행 ID, 큐 커밋, 접수증 SHA-256을 묶는다. 기존 `github-v1` 암호화 문맥과 바이트 호환성을 유지하고 두 문맥 사이 재사용을 거부한다. GitHub 실행 번호를 만들어 넣지 않는다.
4. 신뢰하는 호스트 코드만 `runPreparedLocalJob()`에 검토된 작업기 콜백을 연결한다. 콜백에는 입력 스냅샷 경로·라우팅·문맥·공개 암호화 키·취소 신호만 전달한다. 개인 복호화 키나 GitHub 게시 토큰은 전달하지 않는다. 이 API는 플러그인 또는 사용자 임의 실행 명령을 승인하는 기능이 아니다.
5. 실행 직전 입력을 재검증하고 배타적인 영구 claim 파일을 생성한다. 한 상태 루트의 동일 작업은 동시 호출에서도 한 번만 작업기를 시작한다. 자동 만료·자동 재실행·복구 명령은 없다.
6. 기존 `runProtectedTask()`가 컨테이너와 볼륨을 제거했다고 확인한 암호화 결과만 호스트에 저장한다. 작업기의 성공은 `awaiting-independent-validation`이다. 검증·게시 완료를 뜻하지 않는다.

Docker 복사본에는 호스트의 UID가 남을 수 있다. 작업기를 시작하기 전 별도 초기화 컨테이너가 고정된 메타데이터 처리 코드만 실행해 입력·control 볼륨의 소유자를 작업기 UID/GID 1000으로 맞춘다. 원본 호스트 권한과 복사본의 0700/0600 모드는 넓히지 않는다. 초기화는 네트워크 없음, 최대 100,000개 노드, 요청당 30초, 128MiB 메모리·64 PID·1 CPU로 제한하며 CHOWN/DAC_OVERRIDE 외 capability를 제거한다. 게임·인증·복사된 스크립트를 실행하거나 파일 내용을 읽지 않고, 심볼릭 링크·특수 파일은 거부한다. 기존 프로젝트가 링크를 필요로 하면 별도 안전한 지원 설계 전까지 실패한다. 초기화 실패 시 실제 작업기를 만들지 않고 컨테이너·볼륨을 정리한다. 실제 작업기는 계속 UID 1000, capability 없음, 읽기 전용 입력/control로 실행된다.

## 준비·조회 CLI

Unix 파일 권한과 소유자를 확인할 수 있는 호스트에서 사용한다. `<receipt-root>`와 `<job-root>`는 모두 Git 체크아웃 밖의 전용 비공개 경로여야 한다.

```sh
node scripts/local-job-cli.mjs prepare <task-id> <job-root> <receipt-root>
node scripts/local-job-cli.mjs status <task-id> <job-root>
```

출력은 ID·상태·문맥·라우팅·암호문 지문이다. 작업 원문이나 원시 오류를 출력하지 않는다. CLI에는 `run` 기능이 없으며 GitHub Actions에서는 준비·조회를 거부한다. 공개 CI는 합성 fixture에 한해 로컬 환경을 모사하며 실제 인증정보를 사용하지 않는다.

## 상태와 중단

| 상태 | 의미 |
| --- | --- |
| `prepared` | 입력 준비 완료, 실행 시작 전 |
| `running` | claim 생성 후 작업기 호출 시작. 호스트가 죽으면 이 상태가 남을 수 있음 |
| `awaiting-independent-validation` | 정리가 확인된 암호화 결과 수신. 독립 검증·게시 미실행 |
| `failed` | 정리가 확인된 작업 실패의 암호화 결과 수신 |
| `needs-recovery` | 작업기 예외·정리 불확실·완료 기록 전 확인된 취소, 또는 claim 이후 첫 실행 이벤트 기록 전 중단 |

이벤트는 순서대로 새 파일에만 쓴다. 원자적인 claim 때문에 두 호출이 실행에 진입하지 못한다. 잘못된 저널이나 결과 지문은 오류로 막는다. `running`이나 불완전한 디렉터리를 발견하면 자동으로 재실행하지 않는다. 운영자는 이전 작업기와 자원이 종료됐는지 조사해야 한다. 여러 호스트·서로 다른 상태 루트 사이의 분산 잠금, 전원 장애 후 파일시스템 복구 보장은 아직 제공하지 않는다. 원시 실패 진단의 안전한 장기 보관·조회도 후속 작업이다.

취소 신호는 작업기 반환 직후와 암호문 저장 뒤 확인한다. 마지막 확인 이후 완료 이벤트 추가를 시작하면 완료로 확정하며, 이후 취소는 소급 적용하지 않는다. 취소는 즉각적인 호스트 파일 I/O 중단을 보장하지 않는다.

호스트 콜백은 신뢰 경계에 속한다. 기존 Docker supervisor의 시간·메모리·출력 제한과 강제 정리를 사용해야 하며, 임의 콜백의 종료를 이 모듈이 강제로 보장하지 않는다. 컨테이너에 상태 루트나 복호화 키를 마운트하면 안 된다. 합성 Docker 시험에서 실제 AI를 대신한 fixture가 만든 감사 결과는 실제 모델 검증 증거가 아니다.

## 검증과 미완료 범위

일반 회귀 테스트는 문맥 간 재사용 거부, 접수 뒤 입력 변조, 준비 뒤 변조, 중복 준비, 동시 실행, 취소·실패·정리 불확실, 암호문 변조, 실제 준비·조회 CLI를 검사한다. 별도 실제 Docker 시험은 합성 접수부터 작업기 안의 입력 확인, 공격 fixture 실행, 문맥에 맞는 복호화·구조 검사, Docker 자원 제거까지 확인한다. 네트워크는 `none`, 구독 인증·게임 소스·유료 API 사용은 없다.

실제 구독 런타임 이미지, 실행 호스트 선정, 인증·전송 동의 범위 확인, 게임 기준 테스트, 로컬 문맥을 받는 독립 검증기·게시기, 실패 진단과 복구 UI, 휴대폰 설치 시험은 남았다. 기존 구독 정책 검사와 공개 Actions `prepare-handoff` 차단은 유지한다. 기존 게시기는 GitHub 문맥만 받으며 로컬 결과를 게시하지 않는다. 이번 변경으로 게임 저장소나 기존 PR을 수정·병합하지 않는다.

### 2026-11-17 실행 증거

- 기준 일반 테스트 77/77, 최종 `GITHUB_ACTIONS=true node --test scripts/*.test.mjs` **88/88 통과**, 생략 0.
- 기존 실제 Docker 공격 3개와 신규 로컬 연결·UID 권한 2개 **5/5 통과**, 생략 0. 로컬에 이미 있는 `orchestrator-containment-fixture:local` 이미지를 ID로 고정하고 테스트 파일은 순차 실행했다. 공개 CI도 기존 Docker 단계에 동일 시험을 추가한다.
- JavaScript 구문, Bash 구문, 워크플로 YAML 파싱과 `git diff --check` 통과.
- FIFO 상태 파일에서 읽기가 멈추는 실패를 제한된 자식 프로세스로 재현한 뒤 `O_NONBLOCK`과 일반 파일 검사를 함께 적용했다. 암호문 저장 중 취소 회귀도 수정 검사를 제거한 임시 복사본에서 실패함을 확인했다.
- 독립 읽기 전용 리뷰의 중요 지적 2개(FIFO·저장 중 취소)를 수정했고 재검토에서 범위 내 차단 문제 없음으로 확인했다. claim 직후 중단, 잘못된 저널, 실제 호스트 자식 프로세스 SIGKILL 뒤 재실행 차단도 검사했다.
- 최초 원격 CI는 일반 88개와 기존 Docker 3개를 통과했으나 새 연결에서 실패했다. 로컬의 호스트·작업기 UID가 모두 1000인 조건에서는 드러나지 않았다. Docker 복사본의 UID 보존을 관찰하고 UID 1001 소유·0700/0600 입력이 작업기 UID 1000에서 EACCES가 되는 조건을 별도 볼륨으로 재현했다. 격리 볼륨 초기화로 고쳤으며 권한을 넓히거나 검사를 생략하지 않았다. 입력과 control 양쪽 볼륨을 검사하며 초기화 실패 시 작업기 생성 차단도 확인했다. 초기화 보안 경계의 독립 재검토에서 새 차단 문제는 발견되지 않았다. 실패한 CI를 재실행하지 않고 수정 커밋의 새 실행으로 확인한다.

다음 우선 단위는 로컬 결과의 독립 검증·실패 진단과 게시 권한 경계다. 실제 AI 운영을 열기 전에는 실행 장소와 구독 인증·데이터 허용 범위를 따로 확인해야 한다.
