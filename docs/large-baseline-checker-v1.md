# 대용량 디스크 기준 검사기 v1

Phase 1의 독립 개발 단위다. 실행용 `checks` 디스크 스냅샷의 기준 코드를 메모리 base64 묶음으로 바꾸지 않고 새 Docker 작업 공간으로 전달해 고정 npm 검사 한 단계를 실행한다. 기존 32MiB/파일1MiB 검사기와 `runDiskIndependentChecks()`의 한도는 그대로다. 새 API는 **기준 코드 한 단계의 호스트 관찰**이며 작업 전체·후보 코드 검증·모델 리뷰·게시 승인 보고서가 아니다.

## 전달과 격리

`createDiskBaselineArchive(snapshot,{signal})`는 신뢰한 호스트 코드가 만든 불투명 객체만 받는다. `data-only`, JSON 복사본, Actions 호출은 바이트 생성 전에 거부한다. metadata manifest와 SHA 이름의 일반 파일만 있는 tar 스트림을 한 번 제공하며, 경로·모드·크기·Git SHA1·SHA256·권한을 확인하면서 파일 바이트를 최대64KiB 청크로 읽는다. 전체 원본을 Buffer/문자열로 합치지 않는다. manifest는 별도로 제한된 메타데이터다. 파일 바이트가 전송되더라도 마지막 해시 검사가 끝나지 않으면 전송은 실패이며 프로젝트 코드를 실행하지 않는다.

호스트는 tar를 추출하지 않는다. Docker 자식 stdin으로 backpressure를 적용해 새 입력 볼륨에 복사하고 읽기 전용으로 연결한다. Docker 자식의 종료와 입력 생산자의 종료·파일 닫힘까지 기다린다. 중단/변조와 pipeline이 관찰한 부분 전송·조기 종료는 실패한다. 파이프 쓰기 완료만으로 수신자의 읽기를 증명하지는 못하므로 검증된 생산자 종료와 신뢰하는 Docker cp의 추출 성공 응답을 함께 요구한다. 악성 Docker 데몬은 호스트 신뢰 경계 밖이다. 입력·출력 오류의 원시 내용은 결과에 포함하지 않는다.

기존 디스크 프로필의 합계1GiB·파일128MiB·10,000파일 한도를 그대로 사용한다. 중복 SHA는 한 번만 전송한다. 원래 Unicode 파일명과 Git 실행 모드를 manifest에 유지하고 컨테이너 안에서 정상 경로·모드로 복사한다. 호스트 파일은 실행하지 않는다. 입력 볼륨은 이 전송의 일반 파일과 신뢰한 검사 진입 코드만 담고, 인증정보/캐시 루트의 다른 자료를 mount하지 않는다. Docker cp 전송에 쓰는 seed는 시작하지 않는다.

## 호스트 API

```js
await runDiskBaselineStage({
  diskSnapshot, // checks 목적의 실제 수집/재열기 객체만 허용
  imageId,      // 검토한 기존 로컬 sha256 이미지 ID; 자동 pull 없음
  stage: 'typecheck', // 또는 'unit-test', 'build'
  timeoutMs: 420000,
  outputLimit: 240000,
  signal,
});
```

각 호출은 새 프로젝트·컨테이너·입력 볼륨을 만든다. 먼저 `npm ci --offline --no-audit --no-fund`를 실행하고 설치 스크립트를 생략하지 않는다. 그다음 원래 명령 하나를 실행한다.

- `typecheck`: `npm run typecheck`
- `unit-test`: `npm test -- --reporter=dot`
- `build`: `npm run build`

네트워크 없음, UID/GID1000, root/input 읽기 전용, capability 제거와 no-new-privileges, PID128, CPU2, 메모리/swap3GiB, /work tmpfs2GiB, /tmp128MiB를 적용한다. 단계 간 변경 파일·node_modules·출력은 전달하지 않는다. Docker 클라이언트에는 PATH만 전달하고 컨테이너 npm에는 고정된 최소 환경만 전달한다. GitHub·AI 구독 인증, 개인 키, 호스트 소켓은 전달하지 않는다. Docker 호스트와 같은 UID의 악성 호스트 프로세스는 이 격리 경계에 포함하지 않는다.

입력 복사와 실제 검사 명령에는 각각 최대420초를 적용하고, 제어 명령에는 기존30초와 별도 정리 한도를 적용한다. 따라서 timeoutMs는 호출 전체의 단일 마감 시간이 아니다. 실제 검사 출력은 최대240,000바이트 후 폐기하고 출력 초과를 실패로 남긴다. 메모리 부족 관찰은 resource_limit, 명령 실패는 check_failed, 시간/출력 초과는 timeout/output_limit로 구분한다. Docker/입력 문제도 성공으로 기록하지 않는다. Docker 디스크 공간·호스트 자원이 부족해도 자동 확장/구매하지 않는다.

## 결과와 차단

결과에는 `variant: baseline`, 단계·상태·고정 실패 종류·실제 종료 코드·시간·정리 여부와 관찰한 main 출처/트리/manifest 지문을 넣는다. `publishAuthorized`는 항상 false다. OOM·취소·정리 불확실성을 통과로 바꾸지 않는다. 정리 실패는 결과 승인 대신 예외이고, 취소는 자원 정리 뒤 예외다. 결과의 main 관찰은 수집 당시 정보이며 현재 main이나 서명된 승인 증명서가 아니다.

새 API를 `ai` 큐나 기존 독립 보고서에 자동 연결하지 않았다. CLI 실행·자동 재시도·모델 호출·후보 변경 적용·게시도 제공하지 않는다. 기존 data-only 캐시를 실행용으로 바꾸는 기능은 없다. 실제 비공개 저장소에서 기본 실행 입력 정책에 걸린 자료는 계속 차단한다. 자료를 임의 생략해 전체 게임 검사로 부르지 않는다.

## 검증과 남은 작업

합성 Git fixture의40MiB 자산·Unicode 파일명·실행 파일을 실제 Docker 세 단계에 전달해 해시·모드·UID·인증정보 미전달·읽기 전용 입력·새 단계 상태를 검사했다. 오프라인 의존성 누락·시간 초과·출력 초과는 실패하고 컨테이너/볼륨이 남지 않는 것을 확인했다. 목적/복사 객체/Actions 거부, 소스 변조 뒤 실행 금지, 모호한 생성·정리 실패와 입력 생산자 종료도 검사한다. 합성 타입 검사 스크립트는 실제 게임 TypeScript 검사의 증거가 아니다.

기존 이미지는 실제 게임 의존성 오프라인 캐시를 포함하지 않는다. 실제 게임 기준 검사, 실행 입력 정책의 안전한 처리, 후보 변경과 여섯 단계 독립 보고서 연결, 검증된 오프라인 의존성 런타임, 실제 구독 AI·독립 리뷰·분리 Draft 게시기는 남아 있다. 휴대폰에는 Docker 실행 환경을 설치하거나 새 기능을 배포하지 않았다. 비공개 보관용 캐시를 이번 시험에 사용하지 않았다.

리뷰에서 생성만 된 컨테이너의 기본 ExitCode0을 성공으로 오인할 수 있음을 재현해 수정했다. 새 기준 검사기와 기존 작은 독립 검사기 모두 Status=exited·명시적인 정상 상태 플래그·빈 오류/Pid0·유효한 실행 시작/종료 시각을 요구한다. OOM은 성공으로 처리하지 않는다.

독립 읽기 전용 리뷰의 Important 지적은 미실행 컨테이너의 허위 성공이었으며 실패→통과 회귀로 수정했다. 리뷰어는 수정 후 전체 검사를 독립 재실행하지 않았다. 남긴 Minor는 합성 세 npm 단계가 같은 검사 스크립트를 써서 단계 매핑 교체를 놓칠 수 있다는 점이다. 다음 보고서 통합에서 lifecycle 이벤트/인자 구분 검증을 보강한다. 현재 명령 매핑 자체는 원래 고정 명령 그대로다.

최종 로컬 검증: 전체 단위 테스트 **127/127**, 실제 Docker 합성 테스트 **13/13**, 실패·생략0. JavaScript/Bash 구문·워크플로 YAML·diff 검사 통과. 실제 비공개 게임 코드와 구독 모델을 실행한 결과가 아니다.

후속 [대용량 기준·후보 검증](large-disk-validation-v1.md)에서 별도 후보 입력 API와 여섯 단계 비공개 보고서를 연결한다. 기존 기준 전용 API와 메모리 검사 한도·게시 차단은 유지한다.
